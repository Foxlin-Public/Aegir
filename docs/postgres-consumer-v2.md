# PostgreSQL consumer retained history — Foxlin Industries

This is an unreleased public reference consumer, not the private Aegir engine or a published package. Runtime and SDK use the same format2 implementation/policy. No server database migration is introduced.

First installation explicitly calls `EstablishAsync` in an application-owned existing schema. Normal startup calls `InitializeAsync`, which creates nothing and starts disconnected. Establishment refuses existing state/history, partial tables, independently retained recovery receipts and legacy formats. Legacy journals require separately reviewed reconciliation; do not drop/recreate them to obtain access. The three-argument constructor retains source compatibility but its consumerId must encode a unique stable API/organization/application stream. Prefer the explicit scopeBinding overload. A mismatched binding or policy is refused.

Default upper bounds are10,000 rows per retained receipts/versions/effects/snapshot-receipts/snapshot-group/subject-epoch/checkpoint table and2,000 current snapshot subjects. Every successful changed batch/snapshot consumes an immutable checkpoint; establishment consumes checkpoint0. Lower row and byte bounds may be selected at establishment, never silently changed on reopening. The16MiB byte ceiling accounts exact canonical UTF-8 JSON row and security-head bytes (the non-authoritative connected flag is excluded). It is a logical admission bound, not total PostgreSQL disk/WAL/index size; physical deployment quotas remain operator-owned.

One advisory transaction lock per schema+consumer serializes establishment/open, apply, snapshot, connectivity and read/checkpoint validation. Receipts fingerprint all seven protocol fields. An exact duplicate is validated and processed without new effect/checkpoint growth even at capacity; a reused ID with different transaction/group/subject/type/version fails. Unknown protocol/type or a version gap requests reconciliation, rolling back the entire batch. Every new receipt/effect/version/checkpoint and byte admission shares the same SQL transaction; capacity refusal leaves old state unchanged. No history is evicted.

Snapshots preserve absent-group version and per-subject authorization-epoch high-watermarks and immutable snapshot identities; older versions, reused conflicting snapshot IDs and conflicting same-version group content are denied. Only the disposable reconciled subject view is replaced or invalidated. A snapshot/event never grants authority; protected operations still require fresh canonical server checks and current license/membership. Strict independent business writes still require the opt-in cooperating fencing protocol; journal effects are not arbitrary exactly-once external effects.

The persisted state digest/checkpoint chain detects selective missing/corrupt receipts, versions, effects or metadata. ReadCheckpointAsync returns a nonsecret binding/revision/hash receipt. Retain that receipt outside the database rollback domain before acknowledging the work it covers, and supply it as expectedCheckpoint on restart/restoration. Restoring an older independently copied database then fails closed; a current consistent restoration can reconcile without duplicate journal effects. A receipt covering only an earlier revision cannot prove later unretained work. Lost independent evidence requires operator quarantine, never fresh establishment. SQL integrity alone cannot detect coherent rollback of the whole database plus all external proofs, nor malicious rewriting of every trusted artifact. This reference does not automate the host's independent receipt custody.

No backend credential, user ticket, vendor key or private key is persisted. Secure the application database, schema and independently retained proof location. Resume event processing only after fresh authentication and stream/snapshot reconciliation. Existing SDK package versions remain unchanged; source parity does not certify every historical API or authorize publication.
