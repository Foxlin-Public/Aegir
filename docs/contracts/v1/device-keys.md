# Device public-key management v1

Foxlin Industries. Source contract for the existing POST `/v1/devices/{deviceId}/keys` route (default API path base `/apis`). Package versions and publication are unchanged.

Send one JSON property, `publicKey`, containing a base64 raw ML-DSA-65 public key (1952 decoded bytes). JSON is bounded to8192bytes and the encoded property to4096characters. Duplicate/unknown properties, queries, alternative algorithms/purposes, PKCS#8/private material, EC keys and shared secrets are refused. ML-DSA raw encoding has no elliptic-curve-point format; EC input is an unsupported algorithm. Keep private signing material outside Aegir.

Registration requires current `developer:write`, the device's exact persisted developer realm and a management credential without an application/environment binding. Agents cannot use it. Platform roles do not override ownership. Missing and foreign devices produce the same404. Developer credentials create management-only verification material; they do not approve Human authentication.

A current Human in the same developer realm may explicitly approve their own existing device registration using a non-trusted-device proof issued within five minutes and satisfying currently required authentication assurance. The device must already have its native registration identifier. The immutable approval binds exact device, Human owner, developer realm, native registration, key ID, algorithm and public-key hash. Old keys lacking approval remain denied for Human handoff. This is a server-side approval boundary, not complete native Human enrollment or proof of hardware custody. Personal `mfa:own` is insufficient. Web developer login currently supplies a personal developer realm; obtaining legitimate Human credentials for company-managed devices remains a separate enrollment/issuance limitation.

The response retains `keyId`, `deviceId`, `algorithm` and `enrolledAtUtc`, with `trustUse` equal to `management-only` or `human-owner-approved`. It returns no private material, approval proof or unrelated owner details. All handler responses use `Cache-Control: no-store`. Framework authentication/rate-limit responses may occur before the handler. Errors are sanitized;401/413/415/429may have no body. A503 never proves a mutation committed; inspect current authority and reconcile rather than blindly retrying with stale proof.

The transaction rechecks caller credentials, current epoch, owner, device and revocations under canonical authority locks. Key insertion/rotation, optional approval, epoch and both audit/security facts commit together. Capacity refusal or persistence interruption rolls back all changes. Exact duplicate registration preserves key ID/time; new immutable key identities demote the previous active key. Retired/revoked or other-owner key IDs cannot be reused. Rotation deliberately changes the owner's epoch, so obtain fresh authentication before another mutation.

Signed handoff consumes an approved current key, signs the exact server-generated challenge and relying-party context, checks current device/owner/key/epoch and claims the nonce once. A valid signature is not an administrator grant or external side-effect commit. Enrollment realm and relying-party realm may differ for supported SSO. Replacement/revocation invalidates old preparations and tokens; restored old source rows do not override retained independent authority evidence where supported. Universal same-database rollback detection remains unaccepted.

Lost-device recovery without current independent Human assurance, revoked-device re-enrollment, native hardware custody, push delivery and a full durable native handoff lifecycle remain E3 work. No force-rebind, automatic legacy approval or retired-key resurrection is supplied.
