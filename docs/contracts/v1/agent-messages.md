# Agent message contracts — Foxlin Industries

Source-only contract1.0.0-rc1.e1f. Existing POST /apis/v1/ai/messages accepts transactionId, recipientAgentId, action and base64 payload. Open an Agent-owned transaction first. Sender comes from current authenticated Agent key/JWT, never JSON. POST /apis/v1/ai/messages/receive accepts transactionId and returned envelope; only its current authenticated Agent recipient may open it. Ordinary developer keys do not grant message authority. Both principals need active current owner/tenant/app/environment and messaging scope; same tenant and same application realm only (both legacy-unbound permitted). No Human consent, group/license broker or cross-organization trust is created.

UTF8 JSON only, no Content-Encoding,65536body bytes/depth16; strict unique known fields,256ID/1024action bounds with CR/LF/NUL refused,32768decoded payload bytes. Binary bytes are base64; text payload is not normalized. Actual crypto accepts aegir.pqc.v1/ML-KEM-768/AES-256-GCM/ML-DSA-65 only. Exact newline-delimited canonical15-field header and O-format timestamps bind signature, HKDF context and AEAD AAD. Signature authenticates canonical header; ciphertext is protected by GCM. Sender/recipient keys are server-custodied encrypted PKCS8 under configured KEK; this is not independent endpoint-held or hardware-custody certification. Explicit operational revocation refuses message delivery while historical verification remains a different operation. Rotation can retain old still-usable keys; retired encapsulation private material cannot decrypt.

Successful send means envelope formed and transaction authorization/in-progress facts committed, not recipient delivery. Ciphertext is returned to the caller, not stored in a direct API inbox. A lost send response may leave an InProgress transaction and no rediscoverable envelope; do not retry automatically or infer Abort. Direct send is not cached idempotency: only one send fits Created/Authorized; repeated InProgress send refuses. Correlation alone is not identity. Supported MCP Idempotency-Key remains a separate opt-in exact-intent receipt, with current authority before replay and no receive plaintext replay.

Receive verifies exact outer/header tenant/transaction, stored sender/envelope/key/header hash, current remote principals, public signature and lifetime before private decryption/nonce admission. Local nonce, completion event and audits share canonical SQL commit. Replayed/terminal message returns no plaintext. Valid receipt/completion means Aegir locally opened the message, not that an external business operation completed. No delivery acknowledgment/inbox/background retries/universal exactly-once effect exists. Existing strict fences apply only to explicitly cooperating participants. Restoration never reinitializes independent installation trust; coherent joint rollback/unobserved-revocation guarantees remain separate original obligations.

SDK source send/receive methods use these unchanged camelCase DTOs; package versions/publication status unchanged. HTTP MCP and stdio retain their distinct12tool inventories; only HTTP exposes message adapters. No E1-G or deployment accepted.
