# Retained SDK security and compatibility — Shelf D Pass 2

Foxlin Industries. These are reviewed **unreleased source changes**, not a claim that installed packages were updated. No package, tag or release was published. Java and Go remain source-only. Existing package versions, public operation signatures and keyless-helper retirement remain intact.

All five retained HTTP clients validate bounded HTTPS responses before returning parsed results or adopting exchanged credentials. Default owned transports do not follow redirects or use ambient proxies/cookie stores. JSON requires the expected status/media type, valid UTF-8, bounded bytes/depth/collections and unambiguous security fields. Token lifetime/scope, receipt validity, tenant/application/subject and operation/request identity checks fail closed. Deprecated config-key constructor inputs are retained for compatibility and never transmitted on identity-bearing routes. Diagnostics and client/configuration serialization omit owned credentials and protected payloads; intentional credential-bearing request/response DTOs still require secure handling by the caller.

An injected opaque transport is trusted host code and requires explicit opt-in. Its interface cannot prove the TLS or parsing performed before it returns. In .NET use `TrustedCustomTransport = true` only for a separately reviewed handler; safe default construction owns its transport. Optional development certificate pins are restricted to HTTPS loopback and preserve hostname and certificate-date validation. They change no trust store and are not a production certificate-management procedure.

Native transport, asynchronous callback and response-body waits have explicit cancellation/deadline behavior. Closing clients prevents later credential adoption. Host callbacks can execute arbitrary synchronous code: no SDK can forcibly interrupt a synchronous Node event-loop callback or otherwise guarantee termination of hostile host code. Java/Python/Go bounded worker budgets prevent unlimited abandoned callback workers; their documented ownership and cancellation requirements remain part of the host boundary. Caller-owned transports are disposed by their caller; owned resources are closed by the SDK.

The actual identity HTTP contract takes a **raw stored subject ID**. A developer ID `example_developer` yields a graph named `graph:developer:example_developer`; a raw user ID yields `graph:user:<id>`. A string such as `developer:<id>` is not an implicit API alias for a different stored ID. Retained offline-provider `graph:<subject>` fixtures remain compatible, while unrelated graph IDs fail. Native C# identity enums travel as exact numeric values; portable clients map only known integers to their existing public named enums and send the canonical numeric action type. Unknown/fractional/boolean enum values reject. An exposure response contains `graphId`, not an invented `subjectId`.

Legacy `/security/actions` additionally validates the target server-side. Revoking actions require an explicit known representable node, such as `developer:<raw-id>`, `application:<id>` or `device:<id>`. An accessible subject never authorizes an unrelated target. Unknown, implicit and unsupported user/agent revocation targets fail explicitly rather than reporting a successful no-op. Shared unqualified environment targets require independently current Human platform authority, including reversal. Nonrevoking RequestClarity/VerifyConnection actions remain supported without a target. Developer integrations cannot obtain platform authority through an action or nested context.

Performed and reversed audit entries use distinct IDs; repeating an already reversed action returns its current state. Known historical `allowed`/`denied` audit spellings are read without rewriting the original rows; unknown outcomes fail without guessing. These are compatibility and history-preservation repairs, not authority inferred from audit data.

The retained identity action store is still process-local. Its audit rows persist, but restarting the API does not establish durable legacy action history or transactional reversal. Clearing a reversible coarse resource block is distinct from permanently revoking an issued credential; it is not a guarantee that every otherwise-valid JWT is burned. Use current canonical credential revocation/generation recovery and managed organization ticket epochs for those supported guarantees. No strict atomic fence across a separately committing application database is claimed.

`Aegir/tools/LegacySecurityScenario` and the portable `examples/legacy-security-scenario` consumers exercise seven genuine local operations using a private configuration file. The engineering evidence distinguishes actual Aegir authority from negative synthetic TLS/parser fixtures. Synthetic keys, configurations, database dumps and raw operational logs are excluded from source preservation. Preserve failed receipts; do not treat native test counts as additional .NET cases.
